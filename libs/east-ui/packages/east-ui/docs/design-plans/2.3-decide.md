# 2.3 — Decide patterns (patch-typed commit surfaces)

**Gaps-doc reference:** [`COMPONENT_AND_PATTERN_GAPS.md` §2.3](../COMPONENT_AND_PATTERN_GAPS.md).
**Scope:** The Decide-mode pattern family. Every pattern is *patch-typed* per §0.8 — the recommendation, alternative, or bulk action *is* a `Patch<TState>` and flows through a uniform commit pipeline. Commit friction is controlled by `commitStrength`; reversibility via `East.invertPatch`; audit and undo inherit automatically.

**Type-shape convention (README §Type-shape convention, 0-conventions §3.8):** content (`action`, `rationale`, `impact`, `alternatives`, `options`, `current`, `sortBy`, `compareAgainst`, `primary`, `secondary`, `left`, `items`, `selectionCount`, `selectionLabel`, `summary`, `auditNote`, `dryRun`, `irreversible`, `base`, `patch`), typed patch config (`stateType`, `reversibleFor`, `commitStrength`, `patchFor`), semantic classification (`placement`, `sticky`), state (`committedAt`), and behaviour (`onApply`, `onConfirm`, `onCancel`, `onRun`, `onRevert`) on main. Visual presets (`variant`, `size`, `accent`) + colour slots in `style: OptionType(XxxStyleType)`. `commitStrength` is **config semantic** (drives friction level) — on main, not in style.

**Out of scope:** Configure patterns (§2.5); `DraftPublishBar` lives in Configure even though it's a commit surface, because it's paired with `AssumptionsBar`/`ParameterFormSection` draft semantics.

## 3. Per-entry design

### 3.0 Shared — commit strength

Every patch-emitting commit surface reads from one shared type and one shared resolver:

```ts
// decide/commit-strength.ts
export const CommitStrengthType = VariantType({
    trivial: NullType,        // immediate; no confirm
    standard: NullType,       // CommitConfirmDialog with diff preview
    guarded: NullType,        // confirm + required audit note
    irreversible: NullType,   // typed-confirmation ("type DELETE") + audit note
});

export const DurationType = StructType({
    ms: IntegerType,
});

// Friction resolver: given strength + patch, decide what UX to apply.
// Implemented in the renderer (consumes East IR).
```

Consumers (`ActionCard`, `DecisionBar`, `BatchActionBar`) accept `commitStrength?: CommitStrengthType` and `reversibleFor?: DurationType`. The renderer branches on strength and orchestrates `CommitConfirmDialog` when required.

### 3.1 `ActionCard`

**East IR type:**
```ts
export const ActionCardPrimaryType = StructType({
    label: UIComponentType,
    patch: ExprType,                                       // PatchTypeOf<TState> — caller supplies
    stateType: TypeType,                                   // carries T for renderer inspection
    commitStrength: OptionType(CommitStrengthType),
    reversibleFor: OptionType(DurationType),
    loadingText: OptionType(StringType),
    disabled: OptionType(BooleanType),
});

export const ActionCardStyleType = StructType({
    actionColor: OptionType(StringType),
    rationaleColor: OptionType(StringType),
    impactColor: OptionType(StringType),
    accentColor: OptionType(StringType),
    // inherits Card escape hatches (background, borderColor, ...)
});

export const ActionCardType = StructType({
    action: UIComponentType,                               // headline (e.g. "Reallocate 12 shifts to Area A")
    rationale: OptionType(UIComponentType),
    impact: OptionType(UIComponentType),
    primary: OptionType(ActionCardPrimaryType),
    onApply: OptionType(FunctionType([ExprType /* PatchTypeOf<TState> */], NullType)),
    secondary: OptionType(StructType({
        label: UIComponentType,
        onClick: FunctionType([], NullType),
    })),
    alternatives: OptionType(UIComponentType),             // typically an AlternativesList reference
    committedAt: OptionType(DateTimeType),
    accent: OptionType(ColorSchemeType),
    state: OptionType(StateValueType),
    style: OptionType(ActionCardStyleType),
});
```

**Factory:**
```ts
ActionCard.Root<TState>({
    stateType: TState,
    action, rationale?, impact?,
    primary?: { label, patch, commitStrength?, reversibleFor?, loadingText? },
    onApply: (patch: PatchTypeOf<TState>) => void,
    secondary?, alternatives?, committedAt?, accent?, state?, style?
})
```

**React renderer.** Wraps `Card` (inherits `state` contract). Body layout:
- Top row: `action` (Heading-sized) + `accent` stripe on left edge.
- Middle: `rationale` (Note-variant) + `impact` row (DeltaPill / Numeric).
- Footer: primary Button + secondary Button + "Show alternatives" chevron.

**Commit flow (patch-aware):**
- `commitStrength: trivial` — click primary → `onApply(patch)` directly. Optionally toast "Applied" and record inverse via `East.invertPatch` into a local reversibility window (per `reversibleFor`), surfaced as an "Undo" toast action.
- `commitStrength: standard` — click opens a `CommitConfirmDialog` wired with `{ base: currentState, patch, stateType, summary: impact }`. Confirm calls `onApply(patch)` with optional audit note.
- `commitStrength: guarded` — same as standard but the Textarea for audit note is `required`.
- `commitStrength: irreversible` — renders Dialog with a typed-confirmation Input (must type e.g. the action's label, or a fixed sentinel).

After a successful apply:
- If `reversibleFor.ms > 0`, renderer stores `{ inverse: East.invertPatch(patch, TState), expiresAt: now + ms }` in a local map and surfaces a Toast with "Undo" action for `ms`.
- `committedAt` is set by the caller after successful apply (for audit / timeline indication in the card footer).

**Tests:**
- IR round-trip with each `commitStrength` value.
- `onApply` receives the exact patch.
- Guarded mode blocks submit when audit note empty.
- Irreversible mode blocks submit when typed confirmation doesn't match.
- Undo toast appears with `reversibleFor` set; its action dispatches `onApply(inverse)`.

**Examples:**
| Name | Description |
|---|---|
| `actionCardReallocate` | "Reallocate 12 shifts to Area A" with trivial strength; toast + undo |
| `actionCardStandardConfirm` | Standard with diff preview |
| `actionCardGuardedWithAuditNote` | Guarded with required audit note |
| `actionCardIrreversibleDelete` | Typed confirmation for irreversible delete |
| `actionCardWithAlternatives` | Primary + embedded AlternativesList |
| `actionCardLoading` | `state: loading` skeleton |
| `actionCardCommitted` | `committedAt` set → renders audit stamp |

### 3.2 `AlternativesList`

```ts
export const AlternativeOptionType = StructType({
    label: UIComponentType,
    rationale: OptionType(UIComponentType),
    impact: UIComponentType,
    confidence: OptionType(UIComponentType),               // UncertaintyBadge
    runtime: OptionType(StringType),
    patch: ExprType,                                       // PatchTypeOf<TState>
});

export const AlternativesListStyleType = StructType({
    // inherits OptionList escape hatches
    currentBackground: OptionType(StringType),
    currentBorderColor: OptionType(StringType),
});

export const AlternativesListType = StructType({
    stateType: TypeType,
    options: ArrayType(AlternativeOptionType),
    onCommit: FunctionType([ExprType /* PatchTypeOf<TState> */], NullType),
    current: OptionType(StringType),                       // option id already committed
    sortBy: OptionType(VariantType({ impact: NullType, confidence: NullType, runtime: NullType })),
    compareAgainst: OptionType(StringType),                // option id to diff others against via East.diff
    state: OptionType(StateValueType),
    style: OptionType(AlternativesListStyleType),
});
```

**Factory.** `AlternativesList.Root<TState>({ stateType, options, onCommit, current?, sortBy?, compareAgainst?, state?, style? })`.

**Renderer.** `OptionList` (§1.9) with per-option rows rendering label + impact + confidence + runtime. Commit button per option fires `onCommit(option.patch)` through the same friction pipeline as ActionCard (accepts commitStrength via option or inherits a wrapper `DecisionBar.commitStrength`). `current` option gets a distinct background + "current" chip. `compareAgainst`: for each other option, renderer displays a tiny "vs recommended" chip powered by `East.diff` (e.g. delta hours / delta cost).

**Tests:**
- `sortBy` ordering.
- `compareAgainst` produces diff chip per non-current option.
- `onCommit` receives the patch.

**Examples:** `alternativesListThreeOptions`, `alternativesListWithCurrent`, `alternativesListWithComparison`.

### 3.4 `CommitConfirmDialog`

```ts
export const CommitConfirmDialogStyleType = StructType({
    // inherits Dialog
    irreversibleAccentColor: OptionType(StringType),
});

export const CommitConfirmDialogType = StructType({
    stateType: TypeType,
    patch: ExprType,
    base: ExprType,                                        // current TState
    summary: OptionType(UIComponentType),
    irreversible: OptionType(BooleanType),
    dryRun: OptionType(BooleanType),                       // if true, compute but don't emit
    auditNoteRequired: OptionType(BooleanType),            // true when strength is guarded/irreversible
    typedConfirmation: OptionType(StringType),             // required input text for irreversible
    onConfirm: FunctionType([ExprType, OptionType(StringType) /* auditNote */], NullType),
    onCancel: FunctionType([], NullType),
    style: OptionType(CommitConfirmDialogStyleType),
});
```

**Factory.** `CommitConfirmDialog.Root<TState>({ stateType, patch, base, summary?, irreversible?, auditNoteRequired?, typedConfirmation?, onConfirm, onCancel, style? })`.

**Renderer.** `<Dialog.Root>` (§1.12). Body contents:
- `summary` (Note-variant) at top.
- `DiffView` rendered with `{ stateType, base, after: East.applyPatch(base, patch) }` (mode: `unified` by default; toggle to `side-by-side`).
- Optional `Textarea` (Audit note) — required if `auditNoteRequired`.
- Optional typed-confirmation `Input` — shown iff `typedConfirmation` set; submit disabled until value matches.

Irreversible badge (top-right) tinted with `irreversibleAccentColor`.

**Tests:**
- DiffView content equals `East.diff(base, East.applyPatch(base, patch))`.
- Audit note gating.
- Typed confirmation gating.
- `onConfirm` receives patch + optional note.

**Examples:** `commitConfirmStandard`, `commitConfirmGuarded`, `commitConfirmIrreversible`.

### 3.5 `BatchActionBar`

```ts
export const BatchAction_ActionType = StructType({
    label: UIComponentType,
    icon: OptionType(IconType),
    variant: OptionType(VariantType({ solid: NullType, outline: NullType, ghost: NullType })),
    // Per-item patch factory — caller supplies. Renderer composes via East.composePatch.
    patchFor: ExprType,                                    // FunctionType([SelectionItemType], PatchTypeOf<TState>)
    commitStrength: OptionType(CommitStrengthType),
});

export const BatchActionBarStyleType = StructType({
    background: OptionType(StringType),
    borderColor: OptionType(StringType),
    selectionBadgeBackground: OptionType(StringType),
    selectionBadgeColor: OptionType(StringType),
});

export const BatchActionBarType = StructType({
    stateType: TypeType,
    selectionCount: IntegerType,
    selectionLabel: UIComponentType,                       // "N shifts selected"
    actions: ArrayType(BatchAction_ActionType),
    onApply: FunctionType([ExprType /* composed patch */], NullType),
    sticky: OptionType(BooleanType),
    onClear: OptionType(FunctionType([], NullType)),
    style: OptionType(BatchActionBarStyleType),
});
```

**Factory.** `BatchActionBar.Root<TState, TSelection>({ stateType, selectionCount, selectionLabel, actions, onApply, sticky?, onClear?, style? })`.

**Renderer.** `ActionBar` (§1.12). When an action is clicked, the renderer maps each selected item through `action.patchFor(item)`, then composes via `East.composePatch(..., stateType)`, then applies via the normal commit pipeline (respecting `commitStrength`). On `standard+`, opens `CommitConfirmDialog` with the *composed* patch.

**Tests:**
- `selectionCount` of N produces exactly N `patchFor` evaluations.
- Composed patch equals `East.composePatch(patch1, ..., patchN)`.
- `onClear` fires.

**Examples:** `batchActionBarApprove` (N rows → approve all), `batchActionBarReassign`, `batchActionBarWithGuarded`.

### 3.6 `WhatIfList`

```ts
export const WhatIfItemType = StructType({
    label: UIComponentType,
    delta: UIComponentType,                                // DeltaPill summary
    patch: ExprType,                                       // preview patch
    onRun: OptionType(FunctionType([ExprType], NullType)), // override default behaviour (cached → live compute)
    estimatedRuntime: OptionType(StringType),
    staleness: OptionType(VariantType({ live: NullType, cached: NullType })),
});

export const WhatIfListStyleType = StructType({
    labelColor: OptionType(StringType),
    runtimeColor: OptionType(StringType),
    cachedIndicatorColor: OptionType(StringType),
    liveIndicatorColor: OptionType(StringType),
    // inherits OptionList style
});

export const WhatIfListType = StructType({
    stateType: TypeType,
    items: ArrayType(WhatIfItemType),
    title: OptionType(UIComponentType),
    selectedKey: OptionType(StringType),
    onSelect: OptionType(FunctionType([ExprType /* patch */], NullType)),
    state: OptionType(StateValueType),
    style: OptionType(WhatIfListStyleType),
});
```

**Factory.** `WhatIfList.Root<TState>({ stateType, items, title?, selectedKey?, onSelect?, state?, style? })`.

**Renderer.** `OptionList` (§1.9) vertical list. Each item row:
- `label` — the hypothesis headline.
- `delta` — right-aligned DeltaPill.
- `staleness` chip (`live` = brand accent, `cached` = neutral) with tooltip "Last computed N min ago".
- `estimatedRuntime` caption.

Clicking an item: if caller supplied `onSelect`, fire it with the patch. The parent commonly stacks what-ifs by composing selected patches into a draft via `East.composePatch`. If `onRun` is set on the item, it's a "recompute with live solver" action; renderer exposes that as a secondary button on the item.

**Distinction from `AlternativesList`.** AlternativesList *commits* (applies the patch). WhatIfList *previews* (composes into a staged patch held by the parent). Don't merge — document in header.

**Tests:**
- Select fires `onSelect` with item.patch.
- Staleness chip colouring.
- Disabled state renders `live/cached` indicators muted.

**Examples:** `whatIfListMultiStep` (stackable items → composed staged patch), `whatIfListCachedOnly`, `whatIfListWithLiveRun`.

## 4. Contract compliance

- **§0.1 States** — `ActionCard`, `AlternativesList`, `WhatIfList` inherit `Card.state` fallbacks. `CommitConfirmDialog` itself is ephemeral; the card that triggered it may be in `loading`.
- **§0.2 A11y** —
  - Dialog focus-trap per §1.14 `FocusScope`.
  - Typed confirmation input has `aria-describedby` pointing at the rule ("type DELETE to confirm").
  - Audit note textarea has required `aria-invalid` state when empty.
  - Reversibility toast with Undo action: Undo button is keyboard-reachable; Escape dismisses the toast.
- **§0.3 Colour/dichromacy** — irreversible accent paired with icon + label. Commit strength badges paired with text ("irreversible"), never colour alone.
- **§0.4 Responsive** — `DecisionBar` collapses `secondary` into an overflow menu under 480px. `AlternativesList` switches to stacked `{label, impact, commit}` layout under 600px. `CommitConfirmDialog` sized fullscreen under 480px.
- **§0.5 Hover intent** — Commit strength tooltips (what does "guarded" mean) use shared `HoverIntentType`.
- **§0.8 Patches** — **this is the patch-heavy section.** Every commit surface types its primary operation as `PatchTypeOf<TState>`. Undo is synthesised via `East.invertPatch`. Batch operations compose via `East.composePatch`. Preview is `East.applyPatch(base, patch)`. Diff view in CommitConfirmDialog uses `East.diff`.

## 5. Acceptance criteria

- [ ] Every pattern accepts a `PatchTypeOf<TState>` in its primary operation.
- [ ] `CommitStrengthType` friction pipeline: each strength triggers correct UX.
- [ ] `reversibleFor` produces a working Undo toast within the window; toast dismisses exactly at the window expiry.
- [ ] `BatchActionBar` composes patches via `East.composePatch` and applies atomically.
- [ ] `WhatIfList` items compose into a staged patch on the parent without emitting.
- [ ] `CommitConfirmDialog.DiffView` content equals `East.diff(base, East.applyPatch(base, patch))`.
- [ ] Typed-confirmation gate on irreversible strength blocks submit until match.
- [ ] Audit note required on guarded+irreversible strength.
- [ ] Renderer correctly stores inverse patch for the reversibility window and disposes it after expiry.

## 7. Open questions

1. **Reversibility storage location.** Renderer in-memory map vs `State.bind`? In-memory for v1 (losses on page reload are acceptable for short windows). If users complain, promote to `State.bind` keyed by commit id.
2. **BatchActionBar — atomic vs per-item commit.** Plan spec says composed atomic. Some back-ends prefer per-item rollback. Ship atomic; expose a flag `composition: "atomic" | "per-item"` only if a consumer requests it.
3. **WhatIfList staging UI.** Where's the "staged patch" preview displayed when multiple what-ifs compose? Pattern ships without its own preview — callers wrap a `DiffView` alongside. Consider bundling a `WhatIfStage` helper if ≥2 apps need the same pattern.
4. **Commit strength defaults.** If strength is absent, default to `standard`. Document prominently — the silent default shouldn't surprise authors into bypassing confirm.
5. **Reversibility UI friction.** Should Undo toast replace the action toast, or stack? Replace — a commit is one logical event; two toasts pollute. Display as "Applied · Undo (12s)".

Collections.Planner

The slot-based scheduling primitive. Rows × ordered slots, where rows are typed resources (people, tanks, workstreams, task-types, additive-types) and slots are positions on an axis that can be datetime, numeric (day-of-X, hour-of-Y) or ordinal (phase / stage / week-number). Each cell holds zero or more events in one of three states — committed (audit-locked), proposed (draggable, dirty-patch owned), or rejected (kept for diff). Sub-slot buckets (AM/PM, morning/arvo/night) declared with slotsPerColumn. Roster and Gantt are configurations of this chassis; the slot mental model is the same.

Reading the example
Axis is numeric — day-of-fermentation, not calendar dates. The "now" line at day 7 divides committed past from proposed future. Past cells are read-only; future cells are draggable.
Slots per column is ['AM', 'PM'] — sub-day buckets declared once on the axis. Three slots per column (morning / arvo / night), one slot per column (just date), or an arbitrary labelled array all work the same way.
Conflict marker on GoFerm · day 8 AM — DAP and GoFerm are flagged as incompatible additives by a declared invariant (no-cosolutes-same-bucket). The renderer surfaces the rule's violation as a red ring + corner badge, not host-decorated.
Two flavors of proposed — the dashed teal events are operator proposals (dirty-patch ownership); the italic ones are the model's suggested actions (day 10 pump-over, day 11 malolactic inoculation). Both narrow into Commit.Bar on Apply.
Three event states
StateVisualBehaviour
committed happened Audit-locked, read-only. Solid brand-700 fill. No drag handle. Hover shows provenance (run id, actor, timestamp). To change one, reverse it (creates a new committed reversal) and propose a new one — the history is not edited in place.
proposed ⠿draft Dirty-patch ownership. brand-tint fill, dashed edges, drag handle visible. Drags to move within the surface, off-surface to remove. Commit.Bar applies. Sub-flavours: .added (operator), .model (italic — model's suggestion), .removed (struck through — proposed deletion of a committed event).
rejected declined A proposal that was reviewed and turned down. Kept for diff context; rendered as ink-5 outline with strike-through. Hidden in regular view; surfaces only in compare / journal contexts.
Five column kinds (left side)
KindPurposeBehaviour
identity Row name + sub-label Sticky-left; click selects the row; eyebrow style.
resource The thing the row representsDrop target for items dragged from a sibling Library.
capacity Bounded headroom (hours, kL, FTE)Renders as a small bar + numeric. Drives over-capacity markers in the body cells.
derived Computed from body content Read-only. Recomputes when events change (sum of hours, count of tasks, current fill).
action Per-row controls Small icon button cluster — pin, hide, edit. Right-aligned within the row header.

Drag & drop event grammar
Event kindShapeSurfaces that support it
add Drop new item into a cell (from a sibling Library or palette)Planner.Point · Planner.Span · Roster · Workbench
move Drag a proposed event from cell A to cell B Planner.Point · Planner.Span · Roster
remove Drag a proposed event off the surface (to trash or back to source) Planner.Point · Planner.Span · Roster · Workbench
resize Drag the start or end edge of a span event Planner.Span · Gantt

Three actor roles: source (Library, palette — drag from), target (Planner cells — drag to · within · out), sink (trash, return-to-source). Every surface declares its supported subset; the renderer rejects unsupported kinds at type time. Matrix opts out entirely — its cells render via a free slot, no inherent DnD.

Invariants: Committed events are read-only by construction. Editing the past would corrupt the audit trail. To change a committed event, propose a new one that reverses it (the model can be configured to do this automatically) — both the original and the reversal stay committed. One axis type per Planner. Mixing datetime and numeric in one surface is forbidden — pick one and stay there. Sub-slot buckets are labelled. slotsPerColumn = ['AM','PM'] labels the buckets explicitly. A bare slotsPerColumn = 2 is rejected — operators need to read the bucket name. Conflict markers come from declared invariants, not the host. Authoring invariants: [{ rule, message, severity }] means every screen that uses the same Planner config flags the same violations the same way. Host-decorated red borders are forbidden. The "now" line is implicit and quiet. The renderer draws a 1px brand-d vertical rule at the boundary between the last committed-allowed slot and the first proposed-allowed slot. A small brand-d pip caps the top of the rule so the visual reads as a marker, not a generic separator. No permanent text label — adding chrome real-estate to host a 3-letter word is wasteful. On hover (across a 12px hit zone around the line), a dark tooltip surfaces the precise position (e.g. now · ferment-day 7 PM). Configurable per row — some resources have no "now" (e.g. a budget planner where every slot is proposed). Variants: Collections.Planner.Point — slot-bound events (the winemaker default, Roster's chassis). Collections.Planner.Span — multi-slot span events (the Gantt chassis). Collections.Planner.Summary — read-only roll-up view; no DnD, no Commit.Bar ownership; events are grouped by another dimension. Collections.Planner.Template — recurring-event templates that materialise into proposed events on contact (specced below).

Variant · Collections.Planner.Template

A reusable recurring-event pattern. Authored as a {rule, range, slot, event} tuple; dragged from a sibling palette onto the canvas, it materialises into a set of proposed events the operator can edit individually. Once instantiated, events lose their template link — each is a peer of every other proposed event for edit / commit / reject. The template itself is configuration, not state; deleting it does not remove the events it materialised.

Use cases: Winemaker dosing schedules (2× daily pump-overs across primary), periodisation cycles (a week of training intensities), maintenance routines (Friday safety checks per quarter), kit prep checklists, MLF nutrient additions. Rule grammar (initial): every day · every other day · weekly on D · first of month · days [list]. More complex schedules go through Cause.SupplyDemand or a custom rule function (rule: fn(day) → boolean). Templates vs events: A template is configuration with a known set of materialisations. An event is state with provenance. They never co-exist on the canvas: once instantiated, only the events remain. Editing the template after instantiation does not retroactively change the instantiated events — it changes only future instantiations.

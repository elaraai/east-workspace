Slice.Frame Anchor

The card that holds a chrome-less slice-bound visual. A frame role specialised for slice consumption — same chassis as §1.5b · Frame, but with a fixed three-zone anatomy and an opinionated derived-count footer. Every chrome-less slice consumer (Table, Chart, Stat) is wrapped in one; if there is more than one slice on a page, there is more than one Slice.Frame. Components that own their own frame (DecisionQueue, DecisionJournal) mount the slice cluster into their own eyebrow instead — see the mode lede. The author fills the body slot with the visual; the eyebrow and footer take care of slice chrome.

The eyebrow has exactly two presentations. ① The summary — one row, always: chips compress along the ladder below but the eyebrow never grows a second row and never partially expands. ② The editor — the full multi-row clause view, which is Slice.Edit: an anchored popover floating over the body. There is no in-between state. Collapsing the editor returns directly to the one-row summary; the chassis and the content beneath never move.

Zone rules: Eyebrow — one row, two zones. Left flexes (Filter chips · Breakdown chips · search box) and follows the compress ladder. Right is fixed-width and holds derived meta (freshness chip, count, action button). Never wraps. Eyebrow height 44 px · padding 8 / 12 px. Compress ladder (in order): ① every chip whole · ② trailing chips fold within their family into +M more (filters fold first; the cohort pill folds last) · ③ each family collapses to its count chip (3 filters · breakdown chip · range chip) · ④ terminal — one chip for everything (N narrowed). A chip has one canonical form and renders whole or not at all — never clipped mid-chip, never a degraded variant. Every rung is one row; every chip on every rung opens Slice.Edit — compression changes what is shown, never what is reachable. Horizontal pressure is the eyebrow's problem; completeness is the editor's: the popover is fixed-width, grows vertically, sections per family, scrolls internally, and always shows every clause. The eyebrow never renders a second row and never expands in place. Body — the consumer renders here. The frame supplies no padding; the consumer manages its own gutters. Body content may wrap to multiple rows; a body wrap never re-flows the chrome. Footer — derived count by default, supplied by the frame from Slice.apply.where(...).length. Author can override with a custom node (Slice.Summary, Provenance, paging). Hide with footer={none}; never display "0 rows" without context. Footer height 38 px · paper-2 background.

Invariants: One Slice.Frame per slice. If two slices share a page, they get two frames. The page Header (page-wide Scope.*) is not part of the frame chassis. The frame never grows or shrinks when an affordance opens an editor. Editing happens in a Slice.Edit popover over the body; the chassis stays the same height. This is non-negotiable — see the next pattern. The body reads slice; the body doesn't author slice. A Table inside a Slice.Frame may render sort arrows that write to slice.setSort, but it never opens a filter editor on its own — that's the eyebrow's job. The body produces clicks; the eyebrow houses the affordances that consume them. Variants: Slice.Frame.Compare — two side-by-side frames sharing one slice with different ranges (see Stat.Comparison). Slice.Frame.Embed — chrome-less variant for embedding inside another container (no eyebrow, no footer; only the body slot survives). Used when the parent owns the slice affordances. Framed surfaces: a component that already owns a frame (DecisionQueue, DecisionJournal) is never wrapped — it takes slice as an option and mounts the same eyebrow cluster (chips + edit trigger) into its own header row, right zone. Same chips, same Slice.Edit, one frame.

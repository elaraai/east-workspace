§ 2.2

Slice

Anchors · Slice.Frame · Slice.Edit

The read-side data-narrowing primitive. One SliceHandle<T> per data domain, bound once at the surface boundary; affordances around it write, consumers around it read narrowed data through Slice.apply.where. Slice doesn't render anything that shows the data — that's the consumer's job (Table, Chart, Stat). The architectural rules live in §1.5c · Slice composition; this document specifies each affordance, the container that holds them, and the shared edit overlay.

Where the slice lives — the eyebrow hosts the slice; the slice never owns the frame. The slice affordances (cohort pill · filter chips · range · search · the edit trigger) form one reusable slice cluster. Chrome-less body components (Table, Chart, Matrix, Stat) get framed by Slice.Frame, which supplies an eyebrow and mounts the cluster into it. Components that already own a frame and eyebrow (DecisionQueue, DecisionJournal) are never wrapped in a Slice.Frame — they take the slice handle as an option and mount the same cluster into their own eyebrow. One frame, one eyebrow, everywhere. There are no fused per-consumer wrappers (no Slice.Chart, no Slice.Table) — the body is just a child reading Slice.apply.where.

Slice is read-side; Scenario is write-side. Adding a filter, picking a range, or switching a cohort never produces a dirty patch — it's view state. Commit.Bar never sees a slice change. For write-side narrowing of proposed futures (alternative plans on a Planner / Roster / Gantt), see §1.5d · Scenario composition — same architectural shape, different commit semantics. A page can have both a slice and a scenario active at once; the slice narrows which records are shown, the scenario decides which proposed-events overlay them.

Slice.Frame Anchor

The card that holds a chrome-less slice-bound visual. A frame role specialised for slice consumption — same chassis as §1.5b · Frame, but with a fixed three-zone anatomy and an opinionated derived-count footer. Every chrome-less slice consumer (Table, Chart, Stat) is wrapped in one; if there is more than one slice on a page, there is more than one Slice.Frame. Components that own their own frame (DecisionQueue, DecisionJournal) mount the slice cluster into their own eyebrow instead — see the mode lede. The author fills the body slot with the visual; the eyebrow and footer take care of slice chrome.

The eyebrow has exactly two presentations. ① The summary — one row, always: chips compress along the ladder below but the eyebrow never grows a second row and never partially expands. ② The editor — the full multi-row clause view, which is Slice.Edit: an anchored popover floating over the body. There is no in-between state. Collapsing the editor returns directly to the one-row summary; the chassis and the content beneath never move.

Zone rules: Eyebrow — one row, two zones. Left flexes (Filter chips · Breakdown chips · search box) and follows the compress ladder. Right is fixed-width and holds derived meta (freshness chip, count, action button). Never wraps. Eyebrow height 44 px · padding 8 / 12 px. Compress ladder (in order): ① every chip whole · ② trailing chips fold within their family into +M more (filters fold first; the cohort pill folds last) · ③ each family collapses to its count chip (3 filters · breakdown chip · range chip) · ④ terminal — one chip for everything (N narrowed). A chip has one canonical form and renders whole or not at all — never clipped mid-chip, never a degraded variant. Every rung is one row; every chip on every rung opens Slice.Edit — compression changes what is shown, never what is reachable. Horizontal pressure is the eyebrow's problem; completeness is the editor's: the popover is fixed-width, grows vertically, sections per family, scrolls internally, and always shows every clause. The eyebrow never renders a second row and never expands in place. Body — the consumer renders here. The frame supplies no padding; the consumer manages its own gutters. Body content may wrap to multiple rows; a body wrap never re-flows the chrome. Footer — derived count by default, supplied by the frame from Slice.apply.where(...).length. Invariants: One Slice.Frame per slice. If two slices share a page, they get two frames. The page Header (page-wide Scope.*) is not part of the frame chassis. The frame never grows or shrinks when an affordance opens an editor. Editing happens in a Slice.Edit popover over the body; the chassis stays the same height. This is non-negotiable — see the next pattern. The body reads slice; the body doesn't author slice. A Table inside a Slice.Frame may render sort arrows that write to slice.setSort, but it never opens a filter editor on its own — that's the eyebrow's job. The body produces clicks; the eyebrow houses the affordances that consume them. Variants: Slice.Frame.Compare — two side-by-side frames sharing one slice with different ranges (see Stat.Comparison). Slice.Frame.Embed — chrome-less variant for embedding inside another container (no eyebrow, no footer; only the body slot survives). Used when the parent owns the slice affordances. Framed surfaces: a component that already owns a frame (DecisionQueue, DecisionJournal) is never wrapped — it takes slice as an option and mounts the same eyebrow cluster (chips + edit trigger) into its own header row, right zone. Same chips, same Slice.Edit, one frame.

Slice.Edit Anchor

The single overlay shape used everywhere a compact slice affordance needs more room — and the only expanded form the slice has. The eyebrow summary is state ①; this popover is state ②; nothing exists between them. Anchored to its trigger, fixed width, floats over the body (never pushes or shrinks the content beneath), scrolls internally, dismisses on Apply / Cancel / Esc / click-outside. The full multi-row view lives here, sectioned per family (Cohort · Filters · Breakdown · Range · Search — only active sections render): every clause as a full row, nothing elided regardless of how far the eyebrow ladder has compressed; fixed width, vertical growth, internal scroll. Add-clause and the resolved count close the body. One overlay shape across six interactions: edit a filter predicate · open the filter +M more list · edit a breakdown dimension · open the breakdown +M more list · edit a cohort predicate · pick a custom range.

Invariants: One popover shape. Every Slice.Edit case uses the same head + body + foot anatomy. Only the foot's action grammar varies — listed above. Never resizes the parent. The popover floats over content; opening it does not push the body down. If the popover is taller than the viewport, the body scrolls internally; the chassis below stays in place. Body underneath is non-interactive while open. Click outside dismisses. We do not scrim or grey the body — the operator can still see what they're narrowing — but pointer events on the body are gated until dismissal (or Apply commits). Apply is the only commit path. Edits aren't persisted to the slice handle on every keystroke. Esc / Cancel / click-outside discards. This avoids a half-edited filter writing intermediate states to the consumer. Save as cohort is the only escape hatch for "this filter set is becoming a cohort." It appears in the Filter foot when ≥ 2 clauses are active; clicking opens a small overlay-on-overlay to name and save.

Slice.Legend

Inline rail of swatch + label + value + visibility toggle for a chart. Single density — Legend is always a horizontal row beneath its chart; it has no compact pill form. Overflow aggregates excess series into a single "Others" line.

Slice.Pagination

The position narrowing — a window into an ordered result set. Where Filter narrows by predicate and Range by time, Pagination narrows by offset: which slice of rows you're looking at. Compact is a single bar in a table footer; focused adds numbered pages, page-size, and jump-to. The result count is owned by Slice.Summary — Pagination only moves the window.

Overflow: page list collapses with a single … gap on each side of the active page — always shows first, last, active ±1. Never wraps to a second row. Not a Slice on its own. Slice.Brush

The continuous-range narrowing — drag a window across an x-axis overview to slice to a sub-range. The visual, direct-manipulation cousin of Slice.Range: where Range is a pill + preset list, Brush is a draggable selection over a sparkbar signal, so you see the distribution you're cutting into. Outside the window dims; two handles resize, the body drags. Optionally it reads out values over the selected range.

Values mode (the readout): range resolves to an x-range only; summary adds a live Σ / avg / n over the brushed buckets; values labels each selected bucket with its value. The readout recomputes on every drag — it's the answer to "what's in this window?". Pairs with a chart. Brush is an overview-and-detail control: the brushed range drives a larger chart above it. It owns the x-slice the same way Range does, and emits the same resolved-range contract. Snap: handles snap to bucket boundaries by default (snap=\"bucket\"); continuous snap is opt-in for dense signals. Density: compact (≈28px track, for an eyebrow or filter rail) · comfortable (default, under a chart) · large (≈72px, a standalone overview-and-detail panel). Overflow: n/a — the signal always fits the track width; bucket count is capped so bars stay ≥ 3px.

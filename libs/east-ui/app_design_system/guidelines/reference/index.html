§ 1

Brand & application system

Visual contract

East UI is the application surface of the Elara AI brand. The pattern catalogue below composes @elaraai/east-ui primitives, but every pattern is bound to this section: same palette, same type stack, same density, same status grammar. If a screen breaks one of the rules here, it isn't a pattern — it's a regression.

1.1 · Identity

WordmarkApplication chrome only — never inside content surfaces.
elara.ai DM Sans 700 · −2% tracking · brand-dd / brand mid-stop
VoiceHow the application speaks to the operator.
  • Model-as-colleague, not oracle. The system shows its working, names what it doesn't know, and offers the operator an override. Never "the system has decided".
  • Operator-grade, not consumer-grade. Information density wins over whitespace. No emoji, no exclamation marks, no anthropomorphic mascots. Numbers beat adjectives.
  • Plain English, named risks. "Cap of $10k is below the $13k predicted" — not "potential budget exposure detected".
  • Time-anchored. Every figure carries a freshness ("2m ago") or a horizon ("next 2 wks"). Numbers without time are forbidden.

1.4 · Eight rules every screen follows

01
Decision-first density
A screen exists to commit one kind of decision. Dashboards are forbidden. If a surface lists "interesting data" without naming the decision it serves, it doesn't ship.
02
Trust is visible, not implied
Every output names its run, its input hash, its sources, the assumptions it ran under, and the freshness of each feed. Trust.* renders this at four densities.
03
Override is first-class
Every commit surface offers the canonical cluster Override · Modify · Apply in that order. Override never hides behind a menu. Reason capture is required.
04
Status is dot + word
No tinted pills, no coloured cards, no badge fills. A 8 px dot in pos/warn/neg/brand plus the uppercase status word. Color carries semantics; form carries hierarchy.
05
Brand-tint = dirty
The pale teal fill #e8f6f7 means an unsaved edit. Used nowhere else — not decoratively, not for selection, not for hover. Reset returns to baseline; apply commits the patch.
06
Banners over modals
Stale data, partial feeds, guardrail violations, change-since-last-visit — all render as in-flow banners next to what they describe. Modal overlays are reserved for blocking confirmation alone.
07
Mono labels frame everything
Section titles, eyebrows, status words, keyboard hints, schema labels, namespace marks — all JetBrains Mono · 10–11 px · 600 · 0.16 em · uppercase. The recurring eyebrow is what gives a screen its rhythm.
08
Composition over invention
New surfaces compose Family.Member primitives from the catalogue. If a screen needs something that isn't already a pattern, the pattern gets specified here first — not invented in the screen.

1.5h · Layout descriptors · size, density, stretch

Every pattern declares its preferred layout along three orthogonal axes. Pages compose patterns honestly — a Scenario.Briefing dominates a row; a Stat.Card sits in a cluster; chrome lives in the eyebrow, not in the Main grid. Without descriptors, every screen drifts into a uniform tile grid and lies about what each surface needs.

Three axesOrthogonal; every pattern picks one value on each.
AxisValuesWhat it means
Size xs · sm · md · lg · full Preferred horizontal extent. xs is chrome-inline (eyebrow chips). sm is a 1/4 cluster slot. md is 1/2 row. lg is 2/3 row. full claims the whole Main row.
Density compact · default · spacious Vertical breathing. compact for chrome (eyebrow, sidebar, commit bar). default for body content. spacious for hero stats and briefings — deliberately tall so they read as anchors.
Stretch fixed · flex · fill Behaviour when more horizontal space is available than the preferred size. fixed stays at its size (Stat.Card). flex grows up to a cap (Reference.Similar). fill absorbs all remaining space (tables, planners).

Composition rulesHow a Main grid honours the descriptors.
  • Main is a 12-column grid. xs = inline only (skip Main). sm = 3 cols. md = 6 cols. lg = 8 cols. full = 12 cols.
  • Rows compose by size, not by count. A row holds patterns whose sizes sum to 12. Mixing sm+md+sm is fine; mixing md+md+sm is not (sums to 15).
  • Full-size patterns sit alone in their row. No tiling Scenario.Briefing next to anything else. The briefing is the room, not the wall.
  • Stretch resolves remaining space. When a row sums to less than 12 (e.g. md+sm = 9), the rightmost flex or fill item absorbs the extra 3 columns. If all items are fixed, the row stops at its declared width and the rest is whitespace.
  • Chrome never lands in Main. Slice.Filter chips belong in the eyebrow of the frame they narrow. Trust.Chip lives next to a number, not as a standalone Main card. The descriptor xs means "I’m not a Main item."
  • Density drives row height. A compact row is ~64 px tall; default is ~140 px; spacious is 240 px+. Mixing densities in a row is allowed; the row grows to the tallest member.

1.5c · Slice composition

How Slice.* surfaces compose with visuals. One SliceHandle per data domain · many affordances around it · every consumer reads the narrowed data through the same handle. This is what makes "filter once, narrow everywhere" actually work — without it, every screen duplicates the apply call and drifts.

The patternOne handle, many surfaces. Affordances write; consumers read.

Apply Every consumer derives its data with one call: Slice.apply.where(slice.read(), config, data) · pass the result wherever a pattern asks for items, rows, series, bins. The narrowing call lives inside the consumer pattern — hosts never pre-narrow.
Rules: One SliceHandle per data domain. Bind it once at the surface boundary (typically next to the route or scope), pass it down by reference. Affordances take SliceHandle<T>, never callbacks. The component dispatches addFilter / setRange internally — developers don't wire these by hand. Consumers take SliceHandle<T> + raw data, not the narrowed array. The consumer calls Slice.apply.where itself — keeps every consumer symmetric and removes the trap where one screen forgets to narrow.

OverflowThe system shape. Per-pattern caps live with each pattern.

Every Slice.* surface has an inline cap. Past the cap, entries collapse into a single +M more control that opens a popover with the full list. The collapsed entries remain semantically active — they still narrow the data through Slice.apply.where; only the chrome stops trying to fit them on one row.

Caps & per-pattern mocks live with each pattern Slice.Filter · Slice.Search · Slice.Breakdown · Slice.Cohort · Slice.Legend
Rules: Visual cap, semantic completeness. The chrome stops trying to fit more past the cap, but the data is always narrowed by every active filter / cohort / range — never silently dropped. One popover pattern. The +M more chip opens a popover with the full list, scrollable, with bulk actions (Clear all, Save as cohort) at the foot. Same popover shape across Slice.Filter and Slice.Breakdown. Aggregation belongs to Legend alone. Filter / Breakdown / Cohort / Range never aggregate — every entry stands. Legend collapses because the consumer (the chart) can't render 50 series legibly anyway; aggregating produces a chart you can actually read. Past-cap is a smell. A frame regularly hitting +10 more is a sign the slice should be saved as a Cohort. Surfaces should hint at this in the popover footer ("11 active filters · Save as cohort →").
Wrapping vs overflow: Chrome compresses, body wraps, nothing scrolls horizontally. Chrome never wraps to a new line. Eyebrows, headers, and the commit bar are one row tall, always. When contents can't fit, the chip family compresses progressively: full label → icon + value → icon-only → +M more. The +M more threshold drops below the inline cap when space forces it — e.g. Slice.Filter's cap of 4 may collapse to cap-2 in a half-width column. Search affordances shrink to an icon-only button that expands on click. Body content may wrap. Legend rows, grid cells, prose, and matrix cells all wrap to multiple rows when the container narrows. A body wrap never re-flows the chrome above it. Horizontal scroll is forbidden in chrome. No overflow-x: auto on chip rows, legends, eyebrows, or headers. Operators must see every active narrowing without scrolling sideways. Tables and timelines are the only exception — their scroll is the medium itself. Two-row eyebrows are a smell. If a frame's eyebrow can't fit on one row at its design width, the surface has too many affordances — move some into a frame-internal toolbar, drop chrome to icon-only earlier, or split the surface.

Rules: Scope is one level above Slice. It holds cross-cutting narrowing that every slice on the page subscribes to (range, cohort, environment, tenant). A slice's effective predicate is scope ∩ slice. Affordances bind to exactly one of Scope or Slice. Never both, never inferred. The header carries Scope.*; each frame's eyebrow carries its own frame's Slice.*. If you want to know which handle an affordance writes to, look at its surrounding region. Linked slices share a selection handle, not a slice handle. The master writes a State<Id>; the detail subscribes to it via linked: [{ from, as }]. The detail renders the selection as an implicit chip — non-removable, brand-tinted, fa-link glyph — so the operator can see where the narrowing came from. No silent narrowing across domains. A scope can't filter on a field that doesn't exist in a slice's domain; the renderer warns at bind time. If two slices share a field by name only (e.g. both have user_id), the scope filter applies to both — that's the feature. Multi-slice without scope is fine. If two frames truly don't share any narrowing, omit the scope and put their affordances in their own eyebrows. The header carries no Slice.* in that case — only navigation.

1.5d · Scenario composition

How Scenario.* composes with the Collections.Planner family (Planner / Roster / Gantt) and any other surface that proposes future state. One ScenarioHandle per surface · scenarios share committed history · they fork only on proposed events. The same architectural shape as Slice: affordances write the handle, consumers read it. Mirrors §1.5c.

Four modesOne default · three on-demand variants for comparing scenarios.
ModeWhen to useBest forCaveats
Switch (default) One scenario active at a time. A pill in the Header flips between saved scenarios. Each scenario shows its own committed past + proposed future. Make a plan, then look at the alternative. No visual overlap, low cognitive load. —
Overlay Both scenarios' proposed events visible simultaneously. Distinguished by side-tint (A = brand-d, B = warn) + a small scenario badge. Cells both scenarios share get a "both" badge. Disagreement becomes the visually loud thing. Where do A and B disagree? Best for point events (Roster / Planner.Point) where slots are discrete. Bad for span events — bars overlap and become unreadable.
Compare Two surfaces side-by-side, each rendering one scenario. Committed past appears in both; future diverges. Stakeholder review. Best for span events (Gantt) where overlay doesn't work. Doubles screen real-estate.
Diff Renders only the events where A ≠ B; everything they agree on stays faint. A focused overlay. Span surfaces where full overlay is unreadable. "What changed between this plan and the last commit?" Hides agreement — useful only if context (the "both" set) is implicit.
The non-negotiable rule: Only one scenario is "active" at any time — the one Commit.Bar commits. Even in Overlay mode, the other scenario is a peer for comparison, not a parallel target. Without this rule the operator can't tell which scenario Apply applies. Switching the active scenario is its own operation, not a side-effect of toggling visibility.

InvariantsThe rules every Scenario.*-aware surface must honour.
  • One ScenarioHandle per surface. Bind it once at the surface boundary; pass it down by reference. Affordances write, consumers read.
  • Scenarios share committed history. Forking the past is forbidden by construction — there's one audit trail. Scenarios diverge only on the proposed-future region (right of the planner-now line).
  • One active scenario at a time. The active scenario is what Commit.Bar commits. Other scenarios visible in Overlay / Compare / Diff are peers for comparison, not parallel targets. Switching active is its own deliberate operation.
  • Mode is a view setting, not a slice. Switching Switch ↔ Overlay ↔ Compare doesn't change which events exist — it changes how they're rendered. URL-bindable so deep-links restore the same view.
  • Per-surface defaults are typed. Roster / Planner.Point default to Switch with Overlay available; Gantt / Planner.Span default to Switch with Compare available; Summary surfaces forbid all comparison modes.
  • Rejected events stay with their scenario. A proposal declined in scenario A is rejected within A; it doesn't bleed into scenario B's history. The diff view can show "rejected in A, accepted in B" as a third state worth flagging.

1.5f · Drag & drop composition

A single typed grammar for moving content between surfaces. Same architectural shape as Slice and Scenario — affordances declare their behaviour through the type system, consumers respect the contract. Four event kinds · three actor roles · per-surface support matrix. Any pattern that supports DnD declares which subset it accepts; the renderer rejects everything else at type time.

Four event kindsEvery drag interaction reduces to exactly one of these.
DragEvent = VariantType({
    add:    StructType({ from: LibraryRefType, into: CellRefType }),                  // new item from a sibling source
    move:   StructType({ from: CellRefType,    to:   CellRefType }),                  // within the surface
    remove: StructType({ from: CellRefType,    to:   VariantType({ trash, source }) }),  // off-surface
    resize: StructType({ event: EventRefType, axis: AxisRefType, edge: VariantType({ start, end }) }),  // span events only
})
Reading the grammar: add is the only kind that crosses a source/target boundary — it's how items leave a Library / palette and land on a Planner / Roster / Workbench. move is intra-surface only; cross-row moves between people materialise as Communicate.Swap proposals (a derived audit representation of a move). remove takes a sink target: either trash (drop into a trash icon, permanent) or source (drag back to the Library — returns to the palette). resize exists only for span events with a duration (Gantt bars, Planner.Span). The axis ref + edge variant gives the renderer enough to know which boundary moved.
Three actor rolesEvery surface declares its role in the grammar.
RoleBehaviourPattern examples
source Drag-from. Holds items that can be added to other surfaces. Never receives drops itself (except as the source sink in a remove event — returning an item to the Library). Collections.Library · template palettes
target Drag-to, drag-within, drag-out. The active surface where items live and move. Holds the slot/cell coordinates that add / move / remove events reference. Collections.Planner · Roster · Gantt · Workbench
sink Drag-onto, never drag-from. Terminal destinations for remove events. The two canonical sinks: a trash icon (permanent removal) and the source itself (return-to-palette). trash icon · the originating Library
Composition: A page can have multiple sources, multiple targets, and at most two sinks (trash + return-to-source). The renderer wires drag-flow by matching declared roles — a Library (source) connects to every Planner (target) on the page automatically; a trash icon connects to every target's remove path. Hosts don't wire DnD handlers by hand.

Visual treatmentHow a drag-in-flight reads at every stage.
StageVisual
At rest Items show a ⠿ grip glyph when hovered (only on proposed events; committed events are read-only and show no grip).
Drag-start The dragged item gets opacity: 0.4; the cursor carries a ghost — a low-opacity clone of the event — that follows the pointer. A drop indicator (1px brand-d line for slot-based drops, 2px brand-d outline for cell-based drops) appears at every valid target.
Valid drop hover The target cell highlights with brand-tint fill and a brand-d outline. The cursor ghost stays visible. Invalid drops (incompatible types, capacity exceeded, invariant violation) show a no-drop cursor and the target stays neutral — never red, never tinted.
Drop committed The dragged item materialises as a proposed event in the target cell with the standard dashed brand-tint treatment. The ghost dissolves over --dur-fast. The Commit.Bar registers the new patch.
Drag cancelled Esc or drop outside any valid target → the ghost returns to origin with a small spring animation. No event fired, no patch dirty.
InvariantsThe rules every DnD-aware surface must honour.
  • Surfaces declare their support; the renderer enforces. A Library that's accidentally given a move handler is rejected at type time, not runtime. Hosts never wire callbacks by hand.
  • Only proposed events are draggable. Committed events show no grip glyph and are pointer-immutable. To change a committed event, reverse it (creates a new committed reversal) and propose a replacement.
  • DnD produces dirty patches via Commit.Bar, never silent state changes. Every drop fires a typed event that funnels through the same commit pipeline as keyboard or click edits. No DnD shortcut writes directly to the data layer.
  • Cross-surface drops require a declared connection. A drag from Library A can land in Planner B only if Planner B's config declares Library A as a permitted source. Implicit cross-surface drops are forbidden.
  • Slot-internal DnD is allowed but invisible to the grammar. A Matrix cell may host its own resize handles, brush selection, or numeric edit — that's slot-owned and never produces DragEvent values. The cell-level slot is a sealed boundary.
  • Drop indicators precede the drop. The operator must see a brand-d outline on the valid target before releasing the pointer. Surprise drops (drop succeeds without prior indicator) are forbidden — the renderer warns at dev time.

Ghost variant (no border, ink-3) is for repeated controls inside dense rows where chrome would compete with the data. Labelled icon-+-text buttons place the icon leading, 8 px gap. Trailing icons are reserved for onward navigation (link arrow) and disclosure (chevron). Never stack two icon buttons without a visible group container or a clear function shift.

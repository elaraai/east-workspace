§ 2.9

Experiment

Anchors · Experiment.Root · Experiment.bind

Decide answers "what should we do". Experiment answers "did the thing we tried actually work — or did the numbers just look that way?" A process engineer frames a plain question against the batch record — did slow cure raise strength? — and the surface does the hard part: it compares like-for-like batches (we slow-cure the weaker material on purpose, so the raw average lies), then tries to break the result before anyone trusts it. The process engineer defines the experiment, so nothing here is pre-written: the answer is a picture — a forest plot, balance bars, colour — composed from the numbers and the columns they picked.

StanceThe process engineer defines the experiment — so the answer is derived, never authored.
Non-negotiables: One registered React component, like Ontology — not a composition of east-ui tags. The author writes one tag, Experiment.Root({ … }); the renderer in @elaraai/e3-ui-components owns the set-up rail, the result deck and the charts (real visx, same primitives as Chart). The East side carries bindings + options, never a UI subtree. The result is composed, not written. Because the process engineer chooses the columns, there is no canned prose. Every word on the result side is one of three things: a column name they picked, a number the function returned, or a status derived by rule (interval clears zero → HIGHER; spans zero → NO CLEAR EFFECT; raw and adjusted disagree in sign → RAW COMPARISON MISLEADING). The picture and the colour carry the meaning. The confound is the whole point, so the picture shows it. Slow cure goes on the weaker material, so the raw average is upside-down. The surface puts the raw bar (red, confidently pointing the wrong way) above the like-for-like bar (green, clearing zero the other side) — the sign-flip is the lesson — and below it, a balance row per confounder showing how far apart the two groups started. All derived from the data. Plain words on the surface; fixed concepts on hover. The process engineer sees "what did you change?", "what else was different about those batches?". The few statistical ideas — like-for-like, placebo test — are explained in Chakra <Tooltip>s on a ? icon (the same hover component as everywhere). These are generic concepts, identical across every experiment, so they're safe to author once. Population & comparison are predicates, built like Slice. "Only this line", "treated = slow-cured ≥ 24h vs compared-with < 24h" — the same .pred-row builder Slice uses, so a counterfactual contrast is a predicate the process engineer can read. Set up, run, commit — durable. Config is staged; Run calls the bound function; Commit writes the framed question + answer + trust to a journal dataset. e3-ui never imports east-py-datascience — the DoWhy/EconML compute lives in a developer e3.function reached over Func.bind.

Experiment.ComparisonConfiguration detail

"Which batches?" and "what's the comparison?" are predicates, built with the same .pred-row editor as Slice. The simple case is one yes/no column; the counterfactual case lets the process engineer define the treated group and what it's compared against — e.g. a cure-duration threshold, or a matched control line. The treated and compared-with predicates compile to two row-filters over the bound dataset; the spec carries them as East Predicate values (the Slice predicate type), so the estimator function receives an unambiguous contrast — no free-text, fully re-runnable.

How the answer readsComposed from numbers + columns. No authored prose.

The estimator returns a small typed Answer. The widget turns it into the picture above by rule — the same rules for every experiment, whatever columns the process engineer picked:

// what the bound function returns — pure numbers + the chosen column names Answer = { outcome: "bond_strength", treatment: "slow_cure", naive: -3.1, effect: 5.2, lo: 3.1, hi: 7.4, nTreated: 240, nControl: 240, nDropped: 31, balance: [{ col: "incoming_grade", treated: 6.1, control: 8.0 }, …] } // the widget derives every word + colour — no sentence is stored anywhere status = lo > 0 ? "HIGHER" : hi < 0 ? "LOWER" : "NO CLEAR EFFECT" // → green / green / amber flip = sign(naive) !== sign(effect) // → the amber "raw & like-for-like disagree" banner banner = flip && `${treatment} sits ${naive<0?'lower':'higher'} on ${outcome} (${naive}); differs most on ${top(balance).col} (${t} vs ${c})` forest = [ row("Raw average", naive…), row("Like-for-like", effect, lo, hi) ] balance = answer.balance.map(bar) // one bar per confounder, length = imbalance heading = `Does ${treatment} change ${outcome}?` // the only fixed template — two column slots

A picture and a colour say it without a paragraph — and they're honest, because they're nothing but the data drawn to scale. The fixed concept tips (like-for-like, shuffle test) are the only authored words, and they never mention the process engineer's columns.

WiringWhere the datascience dependency lives — and where it doesn't.

The widget speaks neutral types and depends only on e3-types. The developer's package owns the one thin estimator function — and the only east-py-datascience import anywhere. Func.bind is the typed channel between them.

Experiment.bind · RootSurface

Experiment.bind({ … }) composes the bindings into one handle (mirroring Decision.bind); Experiment.Root renders it. Payload is descriptors only.

// e3-ui — the author's surface (inside a ui() task) const data = $.let(Data.bind(productionBatches)); const spec = $.let(Data.bind(experimentSpec, { mode: 'staged' })); // process engineer edits, staged const est = $.let(Func.bind(estimateFn)); // (data, spec) → Answer const trust = $.let(Func.bind(refuteFn)); const dose = $.let(Func.bind(doseFn)); const journal = $.let(Data.bind(experiments)); const xp = $.let(Experiment.bind({ data, spec, estimate: est, refute: trust, dose, journal })); return Experiment.Root({ handle: xp }); // developer package — the ONLY east-py-datascience import in the picture const estimateFn = e3.function('estimate', East.function([Batches, ExperimentSpec], Answer, ($, data, spec) => toAnswer(Causal.effect(data, specToConfig(spec))))); // ~10-line bridge
API we'd addThe Causal library is ours to shape.
Three changes make this clean: 1 · Re-home the Causal type definitions into a zero-dep module both east-py-datascience and e3-ui depend on (the Python impl stays put). Then the neutral ExperimentSpec ≡ CausalEffectConfig and the bridge is the identity. 2 · Return the naive estimate alongside the adjusted one (and the per-confounder balance) so the sign-flip picture is drawable directly — today causal_effect returns only the adjusted effect. 3 · Surface per-segment effects. The DML path already computes them (causal_dml_effect); expose [{ segment, effect, range }] and the widget grows a fourth tab — "which segments does it help most?" — the most decision-relevant view, from the same binding model.

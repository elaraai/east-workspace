The Studio and Query libraries: a table, the family's Library pane, and tags

<Studio.Library> and <Query.Library> today are galleries of large cards beside a fixed pane. This version makes each one the table people already know from <Record>, with the same Library pane and rail every other builder-frame component has.

Status

  • Approved 25 Nov 2026, and built under one epic, in the order at the foot of this page. The rules and what each piece owes are in Studio and Query Libraries Spec.md, beside this file.
  • The left pane is the family's Library pane. Tabs of cards, listed by a library prop, as in Roster, Calendar, Plan and Sheet. Project and Data source are fields on the rail and columns of the table, never lists in the pane.
  • The main area is a table, not a gallery. One row a page or a query, read a window at a time. A gallery of wireframe cards shows eight or so at once and has nowhere to put what a person filters by.
  • Tags are a field to filter by, and the rail's editor for a set field takes several values. Who created a page or a query is not in this design.

The same frame. The Data sources tab holds what a new query starts on: a click asks the host for a new query on that source. Recent holds this viewer's runs. A query whose data sources are not bound here still says why on its row, and does not open.

Why a table

  • People know it. It is the table every <Record> draws, with the same rail, the same search and the same Details pane. Nothing here is a control of the library's own.
  • It scales. Rows are read a window at a time, so 20 pages and 20,000 behave alike, and the counts come from e3. Today both libraries read the whole record into the browser.
  • It has room for what you filter by. Tags, the data source and the date sit in columns, where a card had a title and one line.
  • The wireframes are kept where they help: on the Templates cards, and as the preview in Details.

Tags

A tag is text a person gives a page or a query. Each row holds a set of them.

PartHow
Storedtags: Set<String> on the page and on the saved query.
Indexedindex.on(["tags"]). An index on a Set field files a row once for each tag, the way the Roster files a person under each skill.
FilteredA Tag chip on the rail. Its editor is the next section: today's, and the one proposed.
ShownA Tags column in the table.
EditedIn Details, and in the query builder's Save popover beside the name and description. A save is one patch through the record, like any other edit.

Who created a row is not in this design. If it is wanted later, e3 already records who made each commit; a row would need that written onto it to be filtered by.

  • Several tags. Each is a brand chip with its ×, the chip the rail already uses for a chosen value.
  • Any or All. The rail's small segment switch, shown once two are chosen. Any is the default.
  • A list to browse. Every tag with its count, read a window at a time as it scrolls. The search box narrows it.
  • Clear tag at the foot, as every other field has.

Nothing here is a new kind of control. The chip, the switch, the search box, the checkbox rows (the ones a phone's Filters view draws) and Clear are all parts the rail has now. A choice still applies as it is made, with no Apply button, and each count is still the rows that tag would give under the other fields' choices.

A set field whose values are listed as chips, rather than searched, gets the same: several chips can be on, with the same Any · All switch.

  • The list keeps to a few rows and scrolls inside its section, so opening Tag does not push the other fields and the foot out of the popover.

  • On a phone the Filters view is the same model: one 44px row a field, reading "Tag · weekly, exec · Applied", with the editor under the open row. Its values are already drawn there as 44px checkbox rows, which is the list proposed here.

What it takes underneath

  • The narrowing holds several values and the match. Today a set field holds one. A narrowing that is saved, such as a Sheet's saved views, is carried to the new form.
  • Reads that count a row once. A row with two of the chosen tags sits under both in the index. Any merges the tags' rows so each comes once; All keeps the rows under every chosen tag. The N of M count is of those rows.
  • A field's values as a paged list. Today the rail can ask for eight values by their start. The list needs every value with its count, a window at a time.

These are changes to the shared record read, not to the libraries, so they are their own pieces of the epic.

What you write

Green is proposed. The rest is today's API, as the Roster and Record examples use it.

// The page library
const pages     = $.let(Record.bind(d.pages));
const rows      = $.let(Data.bindPaged(d.pages, { indexes: ["pages_by_kind", "pages_by_kind_project", "pages_by_kind_tag", "pages_by_kind_title"] }));
const slice = $.let(Slice.bindRecords("ops.library", {
    rows:      { source: rows, label: "Pages", scope: { kind: ["page"] }, search: ["title", "project", "tags"],
                 fields: { title: { label: "Name" }, project: { label: "Project" }, tags: { label: "Tag" } } },
    templates: { source: rows, label: "Templates", scope: { kind: ["template"] }, search: ["title"], fields: { title: { label: "Name" } } },
}));
return <Studio.Library id="ops" pages={pages} slice={{ slice }}
    library={[Studio.library.templates()]} inspector
    page={open.read()} onOpen={go} />;

// The query library
const saved = $.let(Record.bind(d.queries));
const rows  = $.let(Data.bindPaged(d.queries, { indexes: ["queries_by_source", "queries_by_tag", "queries_by_name", "queries_by_saved_at"] }));
const slice = $.let(Slice.bindRecords("analysis.library", {
    rows: { source: rows, label: "Queries", range: "saved_at", search: ["name", "sources", "tags"],
            fields: { name: { label: "Name" }, sources: { label: "Data source" }, tags: { label: "Tag" }, saved_at: { label: "Saved" } } },
}));
return <Query.Library id="analysis" queries={saved} datasets={{ orders, customers, forecast }} slice={{ slice }}
    library={[Query.library.datasets(), Query.library.recent()]} inspector
    query={open.read()} onOpen={go} />;

library and inspector are the family's props and mean what they mean there: the tabs listed, in order, and no pane when left out. Studio.library.tab(rows, …) and Query.library.tab(rows, …) add a tab of the app's own.

The rules

#Rule
L1Each library is laid out by BuilderFrame: one toolbar, the Library pane, the table as main, Details as the end pane. It draws no border.
L2library lists the Library pane's tabs. Left out or empty, there is no pane. inspector shows Details.
L3Each pane collapses to its rail, floats over the table in a narrow frame, and is a strip tab on a phone. The frame keeps the viewer's choice under id.
L4slice is Slice.bindRecords. Its rows source is the table's rows; a source a tab names narrows that tab's cards.
L5Rows are read a window at a time, in the order e3 returns them. Counts come from e3.
L6Clicking a row selects it. Open in builder on the row or in Details, and Enter, call onOpen in a turn of its own and do nothing else.
L7A card of a tab starts something: a template a new page, a data source a new query, a recent run that run. Each tells the host through onOpen, once there is something to open.
L8Tags are edited in Details and saved through the record's patch.
L9Nothing in the page library says Live or Draft.
L10A new page, once it commits, is told to the host, so its builder opens it. Today it is not.
L11New query follows the rail. With one data source chosen it reads "New query on orders" and starts on it. With none or several chosen it reads "New query" and opens a menu of the bound data sources. Today it falls back to the first bound source.
L12New page follows the rail the same way: it names the one project chosen, and otherwise its popover asks for the project beside the name and the template.

What the two records need

The table's columns and the rail's fields are fields of the record's rows, and a field the rail filters by is one an index is led by. Neither record has them today.

RecordTodayNeeds
Saved queriesRows are structs with name, description, saved_at. The data source is inside the query's root list.sources, the names of the data sources it reads, and tags: each a set of text.
PagesEach entry is a variant, page or template, keyed by { project, page }. It has no fields to show in a column or to index.Each entry a struct with kind (page or template), project, title and tags. It holds no time it was last saved: the builder's Save sends a page's placements and its starting filters as two patches at once, and a time both wrote would make the second a conflict. Templates stay in this record, told apart by kind: a migration step changes one record, so a deploy could not move them into another.

Both are changes to a stored form. Each ships a migration step, and Studio and Query ship the index declarations an app adds to its record. The builders write these records too, so their writes change shape with them.

What is lost

GoesWhat stands in its place
The gallery of large wireframe cardsThe table. The wireframe is in Details, and on the Templates cards.
The pane's Projects and Pages lists, and Data sources as a filter listProject and Data source as chips on the rail and columns in the table.
Sort: Z to A, Recent firstThe order e3 pages the rows in. For saved queries the rail's Saved range finds recent work; a page holds no time.
Search over any part of a title, name or descriptionSearch by the start of a title, a name, a project, a source or a tag.
Dragging a query's card onto the builderOpen in builder. A table row is not dragged.
Live and Draft in the page libraryNothing.

Rulings

  • The table is the main area; the two records change, each with a migration step.
  • Live and Draft go from the page library only. The pages record keeps its draft and its live version, and the builder keeps Publish.
  • The Tag filter above is the rail's editor for every set field, and is part of the same epic.
  • Who created a page or a query is out.

The epic, in the order it lands

  1. The saved queries record. sources and tags on a saved query, the index declarations, the migration step. The query builder's Save writes them, and its Save popover takes tags.
  2. The pages record. Each entry a struct with kind, project, title and tags, the index declarations, the migration step. The Studio builder's writes follow.
  3. The query library. Swapped whole: the frame, the Library pane, the table, the rail, Details and tags.
  4. The page library. The same, with Live and Draft gone and a new page told to the host.
  5. The set filter. Several values with Any · All, the browsable list, and the reads under them, in the shared rail.
  6. Examples and skills. The examples, the e3-ui skill, the showcase.

Each library is swapped in one step, once its record has the fields, so there is no stage where a library has lost its filters. Until step 5 the Tag chip works as today: one tag at a time. Steps 3 and 4 build on the Record table, so they follow the open Record pull requests rather than change the same files beside them.

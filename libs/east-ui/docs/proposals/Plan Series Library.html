Plan · the series library

#590: a template IS a series. The current Plan.template / library cannot work — a Plan's rows DERIVE from data + series, so a row spliced in from make() is not in the data and evaporates on the next render. Nobody finds out until they drop one. Make the library a list of series instead: library = series not currently active, drop = add it to the active list, rows = derived, as always.

Every measurement is lifted from the shipped recipes rather than eyeballed — sliceFrame.ts, sliceEdit.ts, recipes/button.ts — the eye is Slice.Legend's own, and the canvas in figure 1 is a screenshot of the real component.

export default East.function([], UIComponentType, (_$) => (

                match: r => r.kind.equal("shift"),
                label_: r => r.line, chips: (r, k) => [Plan.chip({ … })],
            }),
        ], ArrayType(Plan.Types.Series(OpsRow)));

        // ── 3. the handle. NEW — mirrors Slice.bind exactly ────────────

            all,                   // every family that COULD be shown (carries R)

Three new lines, one new namespace. The series are the ones you already write — key and label are the only additions, and they are phase 1 because a family with no stable identity cannot be ordered, persisted, or named to a user. Plan.families then does for series what Slice does for rows: bind takes a storage key, the full set and a seedable state(); families.active() is the derived feed the canvas consumes, exactly as Slice.rows(...) is for a Table.

This is #590's own shape, verbatim. An earlier draft of this figure added a row-type first argument, renamed the component to Plan.Library and made active() a free function. All three were mine and all three were worse: the series array already carries R; SeriesLibrary being outside the Plan namespace is the point (neither imports the other); and Slice puts methods on handles too (slice.read()).

label_ above is the existing per-row gutter accessor, shown renamed only so this figure can put it beside the family's own label — they are different things and one of them needs a better name before this ships.

No popover anywhere. The item gives the editor its space, the way an expanded Plan row gives its render the canvas — one idiom, in both places. It also removes a level: expand → editor, not expand → rail → popover.
This is the revision, and it makes the design simpler rather than working around a limit. The earlier version had the item reveal a Slice.Rail whose chips opened Slice.Edit as a popover. That worked, but it stacked three levels inside a 286px panel and leaned on “the library cannot be a popover, because a popover cannot open a popover” — a constraint. Rendering the editor BODY inline makes that constraint stop mattering: nothing floats, so nothing can nest wrongly. Body and foot are sliceEdit.ts's own slots at their own values (12/14 body, 14/10 foot, bg.canvas); the only thing dropped is the content slot's popover chrome — border, radius, boxShadow: md — which has nothing left to do.
3 · what this asks of Slice.Editneeds a decision
Slice.Edit is popover-only today. It is not exported; a Slice.Rail chip opens it, and its content slot carries the floating chrome. Mounting its BODY inline means splitting the component in two — the surface (content + head + close) and the editor proper (body + foot) — so a host can render the editor without the popover.

That split is worth having on its own: it is the same shape as every other “chrome vs content” separation in this library, and it would let a Drawer or a settings page hold a slice editor too, which nothing can do today. But it changes a shared component, so it is your call whether it lands here or as its own issue.
The alternative — keep the popover and accept three levels in a narrow panel — is what figure 2 replaced. I do not recommend it, but the mock's earlier revision is in git if you want to compare.

One open question I did not decide

Slice.Legend's item leads with a 14×3px colour swatch. A family has no colour. A legend item is swatch · label · value · eye, and the swatch is how it says which series it is. A family maps to a row KIND, and a kind has no single colour — so I left it out and led with the drag grip instead. The alternative is a per-kind icon in that slot (bars-staggered / table-cells / user-group / flag, which PlanTemplateKindType already names). Swatch, kind icon, or nothing?

Two things the prototype turned up

  • Slice.Legend in visibility mode is not the panel. #590 calls it “arguably the active/inactive rail itself”. Its toggle semantics fit exactly — and I have matched them — but legendRail is a HORIZONTAL inline rail (flex, wrap, 16px gap). The families list is vertical, per-row, with a grip and a config affordance. Reuse the vocabulary, not the component.
  • IconButton cannot switch its icon on an expression. name takes a literal IconName, and display will not take an expression either — so an eye that flips with state cannot be composed from existing parts. Slice.Legend manages it because it is a renderer. SeriesLibrary would too; it is why this is a mock and not a running prototype.

Phasing

  1. Series identity — key / label / sublabel? / icon? on every series kind. Nothing works without it, and it is independently useful.
  2. The families handle + Plan.Library — active set, toggle, order, the panel. This is the deliverable.
  3. Per-family slice — figure 3. Real, but not first.
  4. Options as data — height / aggregate / split are sealed inside each series' closure today, so nothing can read or edit them. Breaking IR change across all seven kinds; needs its own review.

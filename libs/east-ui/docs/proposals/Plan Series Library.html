Plan · the series library

Row series become pickable. A panel lists every series the canvas could show; turning one on brings its rows in, turning it off takes them out, and dragging reorders them. The data never moves — only which series are on screen.

Every measurement is lifted from the shipped recipes rather than eyeballed. The eye is Slice.Legend's own — 9px, last in the row, whole row to opacity .5 when off — and the canvas in figure 2 is a screenshot of the real component.

No popover. The item gives the editor its space and tints it, the way an expanded Plan row tints gutter and plot as one band. Same idiom in both places — and one level fewer than opening a floating surface from inside a 320px panel.
The editor keeps the item's own 12px margins, so nothing steps in or out, and it is not a card inside a card — the tint carries it, not a second border. The conjunction sits in its own 26px gutter so every field box starts on the same x, whether or not the clause has one.

There is no explanatory line under the conditions. An earlier draft printed “18 of 24 rows · the canvas slice still applies on top” there, which was wrong twice: the canvas slice is applied UPSTREAM by the host before the data ever reaches the canvas, so it comes first, not on top — and a rule about how two things compose does not belong on screen every time the panel renders. The count in the header already means “rows this series brings”, so narrowing simply changes it: 24 rs becomes 18 rs, in the brand, with a dot. That also survives collapsing, which a sentence inside the editor never could.

Sign-off

DecisionWhere I landed
Editor opens in placeFigure 3 — the item expands and holds it. Nothing floats, so the “a popover cannot open a popover” problem stops existing rather than being routed around.
Named Plan.SeriesLibraryIt is Plan-typed end to end — it takes Plan series and returns Plan series — so it cannot serve Chart or Table without a shared contract that does not exist. Namespacing does not couple it: Slice.Rail is namespaced and mounts anywhere. The handle is what decouples.
Row counts, including zeroA series whose rule matches nothing would otherwise be switched on to no visible effect.
Click first, drag secondToggling is most of the value and needs no new grammar. Drag earns its place for ordering only.

Two open questions

Heat and buckets are hard to tell apart. Rendered side by side, the IR's declared icons for them — table-cells-large and border-all — are both a 2×2 grid of squares and read as the same mark at 12px. Everything else in the set separates cleanly. Worth swapping one before this ships; the obvious candidate is buckets, since it quantises into lanes and could take something with a column reading rather than a grid one. Flagging rather than substituting, because the icon set is the IR's, not the mock's.
1 · What leads the row — settled: the kind icon. Not a colour swatch: a series maps to a row KIND and a kind has no colour. The icons are not invented either — PlanTemplateKindType already declares one per kind (bars-staggered · border-all · chart-line · table-cells-large · table-list · user-group · flag), so the panel is showing a vocabulary the IR has always had and nothing rendered. The drag grip shares that slot and swaps in on hover, so ordering costs no width and nothing shifts.
2 · The inline editor needs no new component — settled. SliceEditPopover already renders as an in-flow disclosure instead of a popover when it sits in editor density, and slice/density.ts documents that case in exactly these terms: “the terminal surface … nothing opens a further popover”. Slice.Rail already uses it. So the library wraps each series' affordances in <SliceDensityContext.Provider value="editor"> and the popover disappears by itself — nothing shared changes, and an earlier draft of this page was wrong to call it a blocker. The tint, the 12px margins and the hairline stay the library's own container styling.

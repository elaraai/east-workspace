Plan

One shared time axis; heterogeneous rows. A Plan is a grouped canvas whose rows are the existing components' surfaces — Planner allocation lanes, Gantt state-runs, Roster shift chips, Matrix weight cells, Chart measures — mounted against the same axis, perfectly aligned, sliced and reviewed as one. It is the shell those components have been waiting for, and it can retire Gantt, Planner and AlignedStack as standalone surfaces.

§1 · Target state

The whole operation, on one axis

A production & despatch plan at week resolution. A pinned measure chart, a machine group with one row drilled in place, a collapsed group resting as a heat strip, a Planner allocation row, a Roster crew row, a milestone stream — one slice, one now-line, one hover cursor through all of it. Every row's content is its source component's rendering, unchanged — only the shell is new. Queue-driven triage is not part of this surface: e3-ui's DecisionQueue is a separate component a host may mount beside a Plan; the canvas's own review chrome is §9.

§2 · Anatomy

One canvas, one shared time axis

The Plan itself is only the lane canvas + time chrome. Everything else is an existing pattern mounted against its axis: the toolbar is the Slice chrome, the window is Slice.Range, measure rows are Chart layers, allocation rows are Planner lanes. One hover draws one shared cursor through all of it. The Plan draws no frame of its own — the host composes it into a Frame/card like any pattern surface — and queue triage stays in e3-ui's separate DecisionQueue, not here.

§3 · Alignment contract

Aligned by construction, not by convention

Every row — whatever component renders it — mounts into the same two-column template: a fixed gutter and a plot divided into n buckets derived from the slice window ÷ resolution. Rows never own an x-scale; they receive one. That single rule lets a chart sit above the spans that cause it and stay truthful to the pixel — and it is the entire job AlignedStack.PlotGutter used to do across components, now internal to the canvas.

Three kinds, one template. Dashed guides and the now-line fall through every row at identical x. Span bars position continuously (real timestamps on the scale); bucket, heat, table and card kinds quantise to the bucket grid the ruler draws.
  • scale — the canvas owns one timeScale(window, resolution); rows are pure functions of it. Zoom and brush replace the scale, never the rows.
  • gutter — fixed width per canvas (168px desktop). Rows with their own y-axis (charts) print y-ticks inside the gutter's right edge, so plots share the identical left edge.
  • snap — runs carry real start/end datetimes and may cross bucket edges; quantised kinds aggregate into buckets. Both truths coexist on one scale.
  • consequence — AlignedStack as a public layout primitive becomes unnecessary: the Plan canvas is the aligned stack.
§4 · Row kinds

Eight kinds, one grid

Rows are a typed variant — Plan.span · buckets · chart · heat · table · cards · events · group — plus the journey overlay. Each kind keeps its source component's rendered surface exactly as it ships today; the Plan contributes the gutter, the scale and the review vocabulary. Shown one by one on the same 12-bucket window, resting and expanded.

Nested spans — intervals aggregate across nestings, exactly like table rollups. A parent's band is the union of its children's runs, to any depth; the ×k chip is peak concurrency inside the segment. Certainty rolls up pessimistically — a segment containing any proposed run reads dashed — and the band splits at now like every bar. §5 · Groups, grains & scale

Twelve strips, not five hundred rows

The canvas opens with every group collapsed to one heat-strip row — its summary measure per bucket as cell depth. ~500 resources ≈ 12 strips: the whole operation reads in one screenful, and the hot group is obvious before anything is expanded. Expanding a group swaps its strip for rows in place; rows virtualise; search and filters auto-expand only matching groups. Behind the toolbar's grain segment there are three grains of one canvas — GROUP (strips), RESOURCE (rows, the default) and ITEM (trajectories, only ever on a filtered or drilled set). The grain changes rows — never the axis, the charts, the rail or the vocabulary.

§7 · Composing & drag-drop

The canvas is configuration, and configuration is data

A Plan's rows are an East value — so composing one is data entry, not layout code. The host declares a row library: templates pairing a kind with a binding (which measure, which group, which crew set). Users drag a template onto the canvas to add a row where they drop it, drag the grip to reorder, and remove from the row menu. Dropping an entity from search adds its row. The same grammar the Planner and Roster already speak — one onDrag, with canDrop veto — extends to the canvas itself.

§8 · Slice binding

One slice, everything narrows together

The toolbar is the shipped Slice chrome, verbatim: Slice.Cohort / Presets chips (mono, counts muted, brand-tinted when active), the dashed Slice.Filter + filter chip, Slice.Search with its / kbd, the Slice.Range window chip (JUL 1 → SEP 21 · 84d, edit popover with presets and compare), and Slice.Summary's N of M · narrowings line. One slice handle binds the canvas and every chart row — filter once, everything narrows. The spec proposes exactly two additions to Slice.Range: a resolution segment (WEEK / DAY) that re-buckets every bound row (§4·K2), and the horizon strip — a brush density whose handles edit the same Range the chip shows.

§9 · Review & exceptions

Every proposal carries its why — and takes a call

The future on a Plan is a reviewable model proposal, not a schedule someone typed. The review chrome is the one Gantt and Planner already ship — a per-row Decision column and a batch foot; the decision popover behind every diamond is specified with the decision components, not here. Apply solidifies the decision's downstream ghost bars in place; Reject greys them and flags the plan dirty; Rerun re-solves around the rejections. Clean rows rest pre-approved under the routine band's bulk accept. Queue-driven triage (an urgency-sorted decision list) is e3-ui's DecisionQueue — a separate component a host may mount beside a Plan on the same slice; it is deliberately not part of this surface.

§10 · Mobile — 356pt

On a phone, Plan is a review tool, not a canvas

Nobody pans 500 rows on a phone on an ops floor. Two jobs survive the trip: where is it hot (the GROUP grain, as a strip list) and what is this thing doing (one group's rows, or one item's story). Decisions are taken from their diamonds and popovers — the queue app is the separate DecisionQueue. Density relaxes one step — grouped cards on a --paper-2 page, 52pt rows, 40pt targets — and per the mobile shell, navigation is a tab strip at the top of the frame, never a bottom bar. The slice, the bar vocabulary and the wording are identical to desktop; only the layout and the input model change.

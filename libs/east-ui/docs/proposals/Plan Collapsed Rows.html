Plan · the collapsed row

A row focus gives one row the canvas. v2 says its neighbours compress rather than disappear — 16px context strips that keep row order, scroll position and status. It specifies that rule for span rows only, where "bars reduced to 7px marks on the same axis" is unambiguous. This page proposes the equivalent for the other seven kinds, so #591 has a language to build against.

Each figure shows the same row at rest and collapsed, on one shared axis, at the real tokens and type. Everything is derived from the span rule unless the caption says otherwise; anything invented is tagged, and the one genuine fork is marked for your call.

A · tone strip  (recommended)

Each bucket becomes a 7px block whose depth tracks the value, negatives in the negative ink, no-data keeping the 45° hatch. You cannot read the numbers — you can read their shape, which is what 16px can honestly carry. Borrows the heat vocabulary, so it adds nothing new to the language.

B · do not collapse

Table rows stay at full height while their neighbours compress. Honest about the fact that numerals do not shrink — but it breaks the uniform 16px rhythm, and a canvas with several table rows would barely free any space for the focused row, which is the whole point of the gesture.

The hard one. Every other kind has geometry to shrink; a table row has numerals, and a numeral has no small form — at 7px it is a smudge. So the collapsed row cannot be a smaller version of the rest row, it has to be a different encoding of the same data — the same tone strip a chart row collapses to. Two candidates:

Group bands do not collapse. They are wayfinding, not content — they are how you know which rows the strips above and below belong to, and 26px of structure is what makes a wall of 16px strips readable. This is already how links focus behaves (index.tsx excludes kind.type === "group" from the rail branch), so it is consistency rather than a new decision.

The language this proposes

Eight kinds, but only three collapse rules — which is the test of whether this is a language or a pile of special cases. Sort each kind by what its mark actually is:

  1. Geometry marks shrink. span, cards, buckets — the mark already occupies a position and a width on the axis, so it drops to 7px and loses its text to color: transparent. State grammar (fill / outline / dash / warn ring) survives in the border. This is v2's span rule, applied unchanged.
  2. Value marks become a tone strip. heat, chart, table — the mark is a number, and a number has no small form. One block per bucket, depth tracking the value, negatives in the negative ink, no-data keeping the 45° hatch, breach in warn. A heat row already is this, so chart and table collapse into vocabulary the canvas already speaks.
  3. Glyph marks keep their shape and lose their size. events — ● milestone, ◆ decision, ▲ exception each mean something different, so the silhouette is the payload. 8px → 5px, labels drop. Making these transparent would erase the row.

Plus two rules that hold across all three:

  1. Collapse, never remove. Every row stays mounted, in order, at 16px on --paper-2, and the strip is itself the return click target. Status dots survive at 5px. This is v2's RAILS rule — and it is also what keeps the body inside VirtualRows instead of replacing the tree, which is the actual bug in #591.
  2. Structure does not collapse. Group bands hold their 26px. They are what makes a stack of strips readable, and links focus already exempts them.
